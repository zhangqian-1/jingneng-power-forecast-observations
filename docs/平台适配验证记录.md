# 平台接口问题处理说明

本说明针对七站总功率预测的接口对接问题。调用方式为 `POST /api/v1/fluxcast/compute`，请求使用 `point_table + frames`，每次提交七站全部测点的96条历史记录，间隔15分钟，无需 `source_id`。

完整字段和调用样例见 [接口交接说明](接口交接说明.md)。本接口不使用新能源预测数据，也不输出调度费用或碳排放。

## 1. 输出结果如何返回

预测成功时，结果统一放在 `result_point` 数组中，共96条，每条包含：

- `varname`：固定为 `totalPowerForecast`，表示七站合计功率预测。
- `timestamp`：预测目标时间，从请求中最大时间的后15分钟开始。
- `value`：有限浮点数，单位MW。

`event_key` 固定为 `JNH.Fluxcast.Compute`；`varname` 与 `timestamp` 的组合唯一。不返回固定的历史准确率 `accuracy`。

完整结果见 [成功输出样例](../examples/platform_output_example.json)。

## 2. 时间如何处理

历史训练数据已确认为北京时间。平台发送UTC，服务内部转换成北京时间生成模型特征，预测完成后再转回UTC返回。平台不需要额外加减8小时。

返回时间保留请求的格式。例如请求末点为 `2025-10-19T15:45:00Z`，预测首点为 `2025-10-19T16:00:00Z`；空格格式输入则按空格格式返回。

同一请求的96条记录须使用一致的时间格式，并对齐15分钟整刻；格式混用或时间不合法返回HTTP 400，不写入历史缓存。具体支持格式见接口说明。

## 3. 历史数据不足如何处理

模型需要至少672个连续可用历史点，即7天。首次启动时，平台可按时间顺序分批补传，每批96点，服务自动累计。

历史不足时，有效数据仍会缓存，返回HTTP 200及 `result_point: []`，并附 `reason: history_not_ready`、中文说明及当前点数。满足条件后返回96点预测，不再用409表示历史不足。

**平台收到HTTP 200后，仍须检查 `result_point` 是否为空。** 空结果样例见 [历史不足输出](../examples/platform_output_not_ready.json)。

升级时不能直接复用旧时间规则的缓存，应使用新的运行目录，按UTC重新补传历史。正常重启保留本版运行目录即可恢复历史和最近结果。

## 4. 温湿度测点和缺测如何处理

请求须包含七站共35个测点：19个功率、8个温度、8个湿度。测点编码保留原有的点号和冒号，具体编码见 [测点需求清单](测点需求清单.md)。

缺测值推荐写 `null`，也兼容省略该帧的测点字段，但 `point_table` 仍须列全35个编码。处理方式如下：

- 功率缺测按0处理，真实的0和有限负值保留。
- 温湿度缺测时，只沿用该测点过去的真实值，不补0，也不用未来值回填。
- 温湿度历史仍不足以构造模型输入时，返回HTTP 200和空结果，`reason` 为 `weather_history_not_ready`，同时列出缺失测点并记录日志。

相关样例见 [完整输入](../examples/platform_input_example.json) 和 [天气历史不足输出](../examples/platform_output_weather_not_ready.json)。

## 5. 验证结果与部署事项

2026-09-22已完成本地验证：39项检查通过，真实HTTP测试覆盖时间格式、缺测、历史不足及服务重启恢复；六份JSON样例与实际请求、响应一致。

使用七站真实数据滚动预测北京时间2025-10-20至2025-12-31，共73天、7008点，MAPE为 **10.8778%**。本次接口修改未改变模型权重，预测值与修改前一致；历史测试精度不代表未来实时精度。

镜像构建和测试结果以交付包内的 `release.json` 及对应提交的GitHub Actions记录为准，旧版镜像不能代替新版。公司服务器联调仍需完成：核对真实数据调用、UTC时间对应和缓存恢复。部署步骤见 [Docker部署运行说明](Docker部署运行说明.md)。
