## 做了什么

| 对接问题 | 本次处理 |
|---|---|
| 每15分钟收到七站功率，怎样返回合计 | 新增POST实测接口，单帧接收19个功率测点；全部有效才返回总功率，不要温湿度 |
| 功率缺测怎么办 | complete / incomplete / missing三种状态；缺测不补0、不返回部分合计，真实0有效 |
| 如何返回预测偏差 | 只读归档原96点预测，按同一UTC目标时刻匹配；偏差为预测减实测，单位MW |
| 会不会发生8小时时差 | 原预测仍负责UTC与北京时间转换；实测仅按UTC匹配，不重复加减8小时，响应保留输入时间格式 |
| 字符串放在哪里 | 数值放result_point，dataStatus、missingPoints、reason等字符串放extra_info |
| 迟到、重发及重启怎么办 | 独立SQLite保留旧预测批次；同刻实测覆盖更新，选定的预测批次不变；重启保留 |
| 会不会改动预测算法 | 原预测代码、权重、依赖与6个预测样例共28个文件SHA256与实施前一致；原预测缓存不由新模块写入 |
| 如何封装 | 同一个容器内运行两个独立进程，原端口8000、新端口8002；两套运行数据分目录持久化 |

- 部署包测试69项通过，其中新模块33项；原预处理测试8项通过。合计77项，无失败或错误。
- 真实七天历史通过原预测HTTP接口顺序输入，成功返回96点；原预测服务重启后结果与历史恢复，重复预测一致。
- 新实测HTTP接口、预测归档读取及独立服务重启恢复通过。实测调用前后，原预测历史文件与最新结果文件SHA256完全一致。
- 不同合法UTC写法、跨日、精确同刻、重复补传、旧曲线保留、事后预测不可参与偏差、上游不可用及错误请求均有测试。
- Compose配置解析通过，确认只有一个容器服务、两个端口和两个独立挂载目录。GitHub不同测试实例已分开端口及缓存目录。

**真实样例有缺测，不能冒充完整实测。** 现有一天预测输入样例的96帧均缺少至少一个功率值；本次生成的七天样例也没有19点全齐的帧。新模块对此返回incomplete和空数值结果，符合本次确认的规则。原预测仍按原补0规则预测，不受影响。平台希望每时刻都有完整实测总量时，应确保19点实际齐全，不能依靠新模块静默补0。

完整测点求和及55.0偏差的测试使用独立、明确标注的说明用数值，**不是模型实测准确率**。真实模型联合测试验证了接口与隔离性，本次未重跑73天MAPE，也未重新训练。
